# Task 1 — Проверочный лист по безопасности данных (PropDevelopment)

Документ подготовлен для первичного аудита безопасности данных (data-centric) на базе подходов **ISO/IEC 27001 / 27002**  
(классификация информации, контроль доступа, защита данных при хранении/передаче, управление инцидентами, управление поставщиками).

---

## 1) Контекст и границы

**Системы/домены:**
- **Продажи**: витрина продаж, client-tour-app, client-mart-app, client-crm-app, client-mart-estate-app (+ их БД)
- **ЖКУ**: витрина собственника, tenant-core-app (+ БД), CRM собственников (+ БД)
- **Финансы**: accountant-service-1 (+ БД), Active Directory
- **Данные**: хранилище данных, BI/отчётность

**Особые зоны риска:**
- несколько точек регистрации клиента, нет единого контроля master-data и потоков данных
- партнёрские API управляющих компаний (УК) без единых политик безопасности, риск кросс-доступа между УК
- реальные проявления проблемы: **в личном кабинете иногда отображаются данные другого клиента**

---

## 2) Классификация данных (4 уровня)

> Для каждого набора данных фиксируйте: **владелец (Data Owner)**, **система-источник (System of Record)**, **потребители**, **каналы передачи**, **срок хранения**, **основание обработки**.

### 2.1 Публичные данные
**Примеры:**
- маркетинговые материалы, описания ЖК/квартир без привязки к людям
- публичные цены/акции
- публичные страницы витрины продаж
- обезличенная статистика (если действительно обезличена)

**Типовые риски и приоритет:**
- **Искажение — Значительный** (репутация, продажи, юридические риски недостоверной информации)
- **Некачественные данные — Значительный** (несогласованность между витриной/справочниками)
- **Обесценивание — Незначительный** (утечка публичного обычно не критична)

---

### 2.2 Внутренние данные
**Примеры:**
- внутренние справочники объектов/корпусов/квартир (без ПДн)
- метаданные интеграций, техническая документация, схемы взаимодействий
- логи приложений (без ПДн/секретов — в идеале)
- внутренние отчёты (без ПДн)

**Типовые риски и приоритет:**
- **Потеря — Значительный** (срыв бизнес-процессов бронирование→сделка→эксплуатация)
- **Искажение — Значительный** (несколько источников истины)
- **Некачественные данные — Критический** (прямо влияет на дальнейшие решения и сервисы)

---

### 2.3 Конфиденциальные данные
**Примеры:**
- ПДн клиентов и собственников (ФИО, телефон, email)
- данные расширенных анкет
- данные о владении недвижимостью (кто, какой объект)
- финансовые данные по ЖКУ (начисления/платежи), счета, истории оплат
- данные, формируемые в процессе онлайн-сделки (включая документы)

**Типовые риски и приоритет:**
- **Утечка — Критический** (ФЗ-152, штрафы, репутация; уже были симптомы «чужих данных»)
- **Потеря — Значительный/Критический** (невозможность исполнять обязательства, спорные ситуации)
- **Искажение — Значительный** (юридические последствия, ошибки в договорах/платежах)
- **Некачественные данные — Критический** (ошибки идентификации клиента → кросс-доступ)

---

### 2.4 Секретные данные
**Примеры:**
- API-ключи, токены, секреты сервисов
- ключи шифрования, сертификаты, private keys
- сервисные учётные записи, пароли, ключи интеграций с госорганами
- ключи/доступы партнёров УК, платёжных систем

**Типовые риски и приоритет:**
- **Утечка — Критический** (компрометация секретов = возможность массового доступа/утечек)
- **Потеря — Критический** (остановка сервисов, невозможность расшифровки/подписания)
- **Искажение — Значительный** (подмена ключей/сертов → MITM/подмена данных)

---

## 3) Матрица рисков (что смотреть в первую очередь)

### Публичные
- [ ] Контроль целостности контента (процедуры публикации, ревью, журналирование изменений)
- [ ] Единый источник данных об объектах/ценах (анти-дублирование)

### Внутренние
- [ ] Согласованность справочников между доменами (master-data / golden record)
- [ ] Нормы по логированию (не писать ПДн/секреты в логи)
- [ ] Резервное копирование и восстановление (RPO/RTO по критичности систем)

### Конфиденциальные
- [ ] Карта потоков ПДн между системами и внешними сторонами (data-flow inventory)
- [ ] Разграничение доступа (RBAC/ABAC), least privilege
- [ ] Сегрегация данных между УК/тенантами (tenant isolation)
- [ ] Обезличивание/псевдонимизация для витрин/аналитики
- [ ] DLP/контроль выгрузок (особенно из CRM/BI)
- [ ] Политики хранения и удаления (retention & deletion), законные основания обработки

### Секретные
- [ ] Централизованное управление секретами (Vault/KMS), запрет секретов в env/репо
- [ ] Ротация ключей и токенов, контроль срока жизни
- [ ] Раздельные секреты по средам (dev/test/prod)
- [ ] Контроль доступа к секретам и аудит чтения

---

## 4) Чек-лист для аудита (вопросы/проверки)

### 4.1 Управление активами и классификацией (ISO 27001 A.5/A.8)
- [ ] Утверждена политика классификации данных и маркировки
- [ ] Для каждого класса данных определены меры защиты (минимум/обязательные)
- [ ] Назначены **Data Owners** по доменам и по ключевым наборам данных
- [ ] Определены **System of Record** для клиента/собственника/объекта/платежа

### 4.2 Доступ и идентификация (ISO 27001 A.5/A.6)
- [ ] Единые принципы IAM (SSO, MFA для админов, управление ролями)
- [ ] Есть модель доступа к данным по ролям для сотрудников и сервисов
- [ ] Реализована проверка прав на уровне API и БД (не только на фронте)
- [ ] Регулярный пересмотр прав (access review)

### 4.3 Защита данных при передаче и хранении
- [ ] TLS везде (внутренний контур тоже), запрет небезопасных протоколов
- [ ] Шифрование at-rest для БД/бэкапов, управление ключами
- [ ] Маскирование ПДн в логах/трассировках/метриках
- [ ] Отдельные сети/сегменты для критичных БД

### 4.4 Управление интеграциями и поставщиками (особенно УК)
- [ ] Единая политика для внешних API (OAuth2/mTLS/JWT, rate limit, schema validation)
- [ ] Контракты API не раскрывают лишние категории ПДн
- [ ] Проверена **tenant isolation**: партнёр одной УК не имеет доступа к данным другой УК
- [ ] Есть журналирование запросов партнёров и расследование инцидентов
- [ ] SLA/ответственность поставщиков и требования по безопасности закреплены договором

### 4.5 Качество данных (актуальная боль)
- [ ] Устранены дубликаты клиентов (identity resolution / dedup)
- [ ] Синхронизация «клиентского профиля» между точками регистрации
- [ ] Валидации входных данных (email/телефон/идентификаторы) + идемпотентность
- [ ] Мониторинг аномалий: «пользователь видит чужие данные», резкие скачки выдач/запросов

### 4.6 Резервное копирование и восстановление
- [ ] Бэкапы есть, протестировано восстановление (не только наличие)
- [ ] RPO/RTO согласованы с бизнесом
- [ ] Бэкапы защищены (доступ, шифрование, неизменяемость)

### 4.7 Реагирование на инциденты
- [ ] Определены процедуры и роли (кто что делает при утечке/подмене/потере)
- [ ] Настроено централизованное логирование и корреляция событий
- [ ] Пороговые алерты на подозрительные действия (массовые выгрузки, ошибки авторизации)

### 4.8 Соответствие законодательству РФ (контрольный блок)
- [ ] Реестр процессов обработки ПДн (цели, основания, состав, сроки)
- [ ] Модель угроз и меры защиты (по требованиям для ПДн)
- [ ] Согласия/уведомления/права субъектов ПДн реализованы и проверены

---

## 5) Артефакты, которые должны появиться по итогу аудита (минимум)
- [ ] Data Classification Policy (политика классификации)
- [ ] Data Flow Inventory (карта потоков данных между системами)
- [ ] Data Owners & Systems of Record (матрица владельцев и источников истины)
- [ ] Third-party API Security Standard (стандарт интеграций с УК и внешними)
- [ ] Incident Response Playbook (плейбук реагирования)
- [ ] Data Quality Controls (контроли качества данных и мониторинг)
