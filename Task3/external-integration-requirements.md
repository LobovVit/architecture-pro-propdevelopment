# Task 3 — Требования к внешним интеграциям «Умный дом»

Ниже — набор обязательных требований к интеграции PropDevelopment с платформой партнёра для:
- **Интеллектуального домофона** (видео + распознавание лиц)
- **Интеллектуального шлагбаума** (распознавание номера)

Требования сформированы с учётом проблем PropDevelopment:
- слабый контроль data-flow и доступов
- риски утечки ПДн/кросс-доступа между УК
- необходимость соответствия законодательству РФ по ПДн

---

## 1) Требования к безопасности (обязательные)

### 1.1 Принцип минимизации данных (Data Minimization)
- Передавать партнёру **только то**, что необходимо для выполнения функции.
- **Биометрия (лицо)**: по возможности **не передавать** в PropDevelopment и не хранить у PropDevelopment.  
  Рекомендуемая модель: биометрические шаблоны хранятся **у партнёра/на устройстве**, а PropDevelopment управляет **разрешениями/ролями** (кто имеет доступ).
- **Номера автомобилей**: рассматривать как персональные данные (привязка к собственнику/квартире).  
  Хранение — минимально необходимое, с ограничением сроков.

### 1.2 Изоляция арендаторов/УК (Tenant Isolation)
- Интеграция должна гарантировать, что:
  - события/команды одного ЖК/УК **не могут** привести к чтению/изменению данных другого ЖК/УК.
- Требование: в API партнёра должен присутствовать явный контекст **tenant/building_id**.
- Проверки изоляции должны выполняться **на стороне PropDevelopment** (Gateway) и **на стороне партнёра**.

### 1.3 Шифрование и защита каналов
- Все каналы PropDevelopment ↔ партнёр:
  - **mTLS (mutual TLS)** обязательно
  - TLS 1.2+ (лучше 1.3), запрет слабых шифров
- Входящие webhooks партнёра:
  - только через mTLS
  - дополнительно **подписанные** (HMAC/JWS) + защита от повторов (nonce/timestamp)

### 1.4 Управление секретами
- Никаких ключей в репозиториях/конфигах в открытом виде.
- Секреты партнёра (client_secret, ключи подписи webhook, mTLS private keys) хранятся в **Vault/KMS**.
- Ротация ключей:
  - плановая (например, 90 дней) и аварийная
  - без остановки сервиса

### 1.5 Логирование, аудит и расследование
- Логи должны содержать:
  - `correlation_id` / `request_id`
  - `tenant_id/building_id`
  - тип операции (команда/событие)
  - результат (успех/ошибка)
- Логи **не должны** содержать биометрию, изображения лиц, полные номера авто (допустимы маскированные).
- Аудитные записи должны быть неизменяемыми (append-only) и иметь сроки хранения.

### 1.6 Защита от злоупотреблений
- Rate limiting на уровне Gateway:
  - по пользователю
  - по дому/tenant
  - по типу операции (например, открытие двери)
- Idempotency для команд (повтор команды не должен приводить к повторному открытию).
- Circuit Breaker/Retry с экспоненциальной паузой.

## 2) Протоколы аутентификации и авторизации

### 2.1 Пользовательский доступ (Owner → PropDevelopment)
- Мобильное приложение аутентифицируется в PropDevelopment через **OIDC/OAuth2** (JWT access token).
- В PropDevelopment применяются RBAC/ABAC проверки:
  - пользователь → квартира/подъезд/парковка → разрешённые действия

### 2.2 Сервис-сервис (PropDevelopment → партнёр)
Рекомендуемый минимум:
- **OAuth 2.0 Client Credentials** для сервисной авторизации Gateway → партнёр
- обязательный **mTLS**
- короткоживущие access-токены (5–15 минут)

Опционально (если партнёр поддерживает):
- **OAuth 2.0 Token Exchange** (RFC 8693) или OBO (on-behalf-of)  
  чтобы партнёр мог выполнять действие «от имени пользователя», но без передачи пользовательских секретов.

### 2.3 Авторизация на стороне партнёра
- Партнёр обязан поддержать разграничение прав:
  - на уровне tenant/building
  - на уровне устройства (конкретный домофон/шлагбаум)
- Нельзя выдавать партнёру возможность видеть/менять данные иных ЖК/УК.

## 3) Организация взаимодействия между системами

### 3.1 Почему нужен SmartHome Integration Gateway
**Запрещено** подключать мобильное приложение напрямую к API партнёра.
Gateway нужен, чтобы:
- реализовать единые политики безопасности
- централизовать аудит и контроль data-flow
- обеспечить tenant isolation
- минимизировать и нормализовать передаваемые данные
- реализовать ретраи, DLQ, идемпотентность

### 3.2 Сценарии взаимодействия (основные)

#### A) Открыть дверь/шлагбаум (команда)
1) Mobile → Tenant Vitrine: запрос на действие (JWT пользователя)
2) Tenant Vitrine → SmartHome Gateway: команда + контекст (user_id, tenant/building_id, device_id)
3) Gateway:
   - проверяет права (RBAC/ABAC)
   - формирует идемпотентный запрос
4) Gateway → Партнёр: команда (mTLS + OAuth2)
5) Партнёр → Gateway: результат
6) Gateway → Vitrine → Mobile: статус

Требования:
- идемпотентность (idempotency-key)
- лимиты на частоту команд
- журналирование (кто/что/когда/где)

#### B) Авто-открытие по лицу/номеру (событие)
1) Устройство/платформа партнёра распознаёт лицо/номер
2) Партнёр проверяет разрешение (по ранее синхронизированным правилам) и открывает
3) Партнёр отправляет событие в PropDevelopment (Webhook)
4) Gateway валидирует webhook (mTLS + подпись + защита от повторов)
5) Gateway публикует событие в Event Bus (опционально) и/или пишет аудит
6) Данные для BI уходят обезличенно/минимально

Требования:
- webhook security (mTLS + signed payload)
- анти-replay (timestamp/nonce)
- минимизация данных (без биометрии/изображений; номер авто — маскировать)

### 3.3 Модель данных и хранение
- В PropDevelopment хранить:
  - маппинг: `device_id ↔ building_id/entrance_id`
  - правила доступа: `user_id ↔ device_id ↔ permission`
  - аудит и технические метаданные (idempotency keys, статусы)
- Не хранить в PropDevelopment:
  - биометрические шаблоны/фото лиц (если не требуется законом/бизнесом)
  - видео (если не требуется)
- Сроки хранения событий — ограниченные, с политикой удаления.

## 4) Контрольные критерии при приёмке интеграции (Definition of Done)
- mTLS настроен и проверен (сертификаты, ротация)
- OAuth2 работает (client_credentials; короткие токены)
- webhooks подписаны и защищены от повторов
- tenant isolation протестирован (негативные тесты: доступ к чужому ЖК)
- логи и аудит есть, без утечек ПДн/секретов
- реализованы rate limits + idempotency + retry/DLQ
- документирована схема data-flow и состав передаваемых данных
